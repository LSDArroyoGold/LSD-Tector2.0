# Monitoreo de batería por INA219 (voltaje/corriente vía I2C) -- ACTIVO
# desde el 3/9/2026.
#
# HARDWARE: INA219 en serie en el cable positivo principal (entre pack y
# entrada del step-down -- así mide corriente real del sistema, no solo
# voltaje), VCC del propio módulo alimentado del 3.3V de la Pi (pin 1 --
# no necesita estar siempre encendido, solo se lee mientras la Pi está
# despierta), SDA/SCL compartiendo el mismo bus I2C que el DS3231 (bus 1,
# dirección 0x40, sin conflicto con el 0x68 del RTC). Lecturas reales
# confirmadas: 7.596V / 478mA con la Pi corriendo birdnet-lsd normalmente
# -- ambos valores con sentido físico (2S2P Samsung INR18650-35E, ~3.8V/celda).
#
# SOFTWARE: watchdog reactivo tipo v1.1 -- scripts/chequeo_bateria.sh corre
# cada 5 min por cron, SIEMPRE (no solo en ventana, ver nota de
# "CARACTERIZACION DUAL" mas abajo -- unificado el 4/9). Lee el INA219
# (python/registrar_bateria.py) en cada corrida; si ADEMÁS hay una
# ventana activa y el voltaje cae por debajo de UMBRAL_BATERIA_V, marca
# CIERRE_FORZADO=TRUE (fuera de ventana no hay nada que forzar a cerrar).
# inicio_amanecer/atardecer.sh ponen VENTANA_ACTIVA al arrancar la
# ventana; cierre_amanecer/atardecer.sh cierran antes de tiempo si ven
# CIERRE_FORZADO=TRUE (además del cierre normal por horario) y resetean
# los dos flags al terminar.
#
# CARACTERIZACION DUAL (agregado el 4/9/2026, unificado el mismo dia):
# cada corrida del watchdog (python/registrar_bateria.py, en vez de
# leer_ina219.py directo) hace DOS lecturas -- CON el MPPT conectado tal
# cual y SIN carga (aislada) -- y loguea ambas a log_bateria.txt (CSV),
# que se sube a Drive al final de cada corrida (best-effort, nunca
# bloquea la decision de seguridad, que sigue basandose SOLO en la
# lectura SIN carga). Pensado para poder reconstruir despues como se
# comporta el pack en los dos regimenes a lo largo del tiempo --
# seguridad y decision de corte sin cambios, esto es puramente para
# analisis posterior.
#
# Unificado con el chequeo de seguridad en el mismo chequeo_bateria.sh
# (que ahora corre siempre, no solo en ventana -- ver mas arriba) para no
# tener dos mecanismos separados haciendo cosas parecidas.
# python/log_curva_carga.py (el logger exploratorio del rato anterior,
# corriendo suelto por su cuenta) queda retirado/superado por esto --
# sacado del crontab, el archivo se deja en el repo solo de referencia.
#
# Agregado el 4/9/2026: cada corrida tambien loguea temp_cpu_c
# (/sys/class/thermal), throttled (vcgencmd get_throttled -- mismo
# bitmask usado a mano durante el debugging de undervoltage de este
# proyecto, 0x0 = limpio) y load_avg_1min (os.getloadavg()) -- lecturas
# casi gratis al lado de las dos del INA219, pensadas para cruzar despues
# contra voltaje/corriente (ej. temperatura alta por uso real vs. por
# ambiente, o un evento de throttled coincidiendo con bateria baja). Filas
# de log_bateria.txt anteriores a esta fecha tienen menos columnas (CSV
# desparejo a proposito, no se reescribe el historico).
#
# AISLADOR DE CARGA MPPT (agregado y validado el 3/9/2026, esquematico:
# https://claude.ai/code/artifact/f9c178ff-7ef6-41eb-9c7a-5d018edceb9a) --
# leer_ina219.py corta un instante la carga MPPT->BMS (GPIO17, PNP+MOSFET
# dedicados, no el switch principal de alimentacion) antes de cada
# lectura, para que SIEMPRE quede en descarga pura, sin importar si hay
# sol entrando en ese momento. Confirmado con datos reales el mismo dia:
# 7.012V aislado vs 8.476V sin aislar, con el MPPT cargando -- 1.46V de
# diferencia, la lectura cruda hubiera sido groseramente optimista. El
# default seguro de ese circuito (sin nadie manejando GPIO17) es "carga
# conectada", sostenido solo por hardware -- ver el propio leer_ina219.py
# para el detalle de por que el default no puede depender de la Pi acá
# tampoco (mismo principio que el corte de alimentacion, pero aplicado a
# un circuito distinto). Ventana de corte real: ~1.2s cada 5 min, sin
# impacto medible en la carga a largo plazo.
#
# DISEÑO ACORDADO (3/9, sesión con Diego) -- dos partes separadas a
# propósito, no una sola cosa:
#
# 1) CORTE DE SEGURIDAD (lo único que bloquea/cierra ventana): se queda
#    simple, umbral de VOLTAJE puro, sin depender de ninguna curva ni
#    calibración -- cuanta menos lógica tenga la parte de seguridad,
#    mejor, y es lo más robusto. Nunca dispara por porcentaje, ni antes
#    ni después de tener la curva empírica. Umbral ya definido:
#
#      UMBRAL_BATERIA_V=6.9   # ~3.45V/celda, ~15% de capacidad restante
#
#    Motivo del valor: deja ~0.4V/celda de margen sobre el peor caso
#    posible de disparo del BMS (3.05V/celda), cubre la caída IR del
#    propio BMS (<300mOhm) más el intervalo de 5 min entre chequeos del
#    watchdog, y evita ciclar las celdas cerca de su corte de fábrica
#    (2.65V/celda). Detalle completo: cuaderno de laboratorio, 14/8.
#
# 2) PORCENTAJE ESTIMADO (para logs/dashboard, NO gatilla nada): la
#    tensión bajo carga no es la tensión a circuito abierto (OCV) --
#    compensar con la corriente medida en la misma lectura:
#      V_ocv_estimado ≈ V_medido + I_medido × R_interna_del_pack
#    Con el aislador de carga MPPT ya en juego, esta compensación queda
#    más simple que lo pensado originalmente: la corriente medida es
#    siempre de descarga (nunca de carga, porque el MPPT está aislado en
#    el instante de la lectura), así que no hace falta manejar los dos
#    sentidos -- solo la caída IR del propio consumo de la Pi.
#    Despues mapear ese V_ocv a % con una curva. Arrancar con la curva
#    del datasheet Samsung INR18650-35E (nominal 3.60V, carga 4.2V, corte
#    fábrica 2.65V, 3350-3500mAh a 0.2C) como aproximación inicial -- pero
#    esa curva es de UNA celda a 0.2C (680mA) en laboratorio, no del pack
#    2S2P real con BMS y carga variable de este sistema, así que en algún
#    momento reemplazarla por una curva empírica propia:
#
#    PENDIENTE -- corrida de calibración (pedida por Diego, no hecha
#    todavía, dejar para cuando la pida explícitamente):
#      - Cargar el pack a 100% antes de arrancar (ahora estaba a 7.596V,
#        parcial -- para cubrir el tramo alto de la curva hace falta
#        arrancar de lleno).
#      - Desactivar temporalmente los 4 cron de ciclo de ventana
#        (inicio_amanecer/atardecer.sh, cierre_amanecer/atardecer.sh) para
#        que no corten la prueba a mitad de camino -- restaurar el
#        crontab automáticamente al terminar (o si falla algo, con trap).
#      - Dejar la Pi despierta corriendo birdnet-lsd de forma continua
#        (carga real, no artificial de banco) y loguear cada 60s:
#        timestamp, voltaje, corriente, mAh acumulados (coulomb counting
#        UNA sola vez, offline, para construir la tabla -- no en campo).
#      - Frenar en ~6.6V (margen sobre el corte del BMS en 6.1V), no
#        llevarlo hasta el fondo.
#      - Duración estimada: ~12-14hs, al consumo real medido (~470mA
#        promedio) sobre los ~7000mAh nominales del pack 2S2P.
#
#    Una vez que exista la curva real: mirar a qué % corresponde
#    aproximadamente el UMBRAL_BATERIA_V=6.9 actual (~15% según la regla
#    vieja) y, si tiene sentido, ajustar el NÚMERO del umbral -- pero el
#    mecanismo del watchdog sigue comparando contra voltios siempre, la
#    curva nunca pasa a ser parte del disparo en sí.
#
UMBRAL_BATERIA_V=6.9
VENTANA_ACTIVA=NONE
CIERRE_FORZADO=FALSE
